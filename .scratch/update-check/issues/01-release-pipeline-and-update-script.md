# 01 — 发版流水线与更新脚本（首发 0.2.0）

**What to build:** 作者敲一条命令就能发出一个版本——版本号只输入一次、两份清单同步更新、构建产物一并提交、标签推上去、GitHub 上出现一个带说明的 Release。发完之后，任何一台机器把这个仓库 clone 下来，**不装 Node、不跑构建**，直接「加载已解压的扩展程序」就能用；用户双击仓库根目录的更新脚本，就能把自己那份工作副本推进到最新。

这一票不改扩展的任何运行时代码，也不产生任何用户可见的新功能。它是后面三票的地基：远端目前**没有任何 Release 对象**，`releases/latest` 返回 404，在此之前没有任何办法验证更新检查做对了。

规格见 `.scratch/update-check/spec.md` 的「分发与发版」「更新脚本」两节；为什么构建产物反常地进版本库，见 ADR-0011。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 构建产物目录从忽略清单移出并提交进版本库；`.gitignore` 里留一句注释指向 ADR-0011，免得后来的人当脏东西清理掉
- [ ] 构建脚本支持发版模式，该模式下关闭 sourcemap（产物里连映射注释都不留）；日常构建与 watch 行为不变，照旧带 sourcemap
- [ ] 发版命令接受一个版本号参数，依次完成：校验工作区干净（不干净则拒绝执行）→ 把版本号同时写入扩展清单与包清单 → 发版模式构建 → 连产物一起提交 → 打上 `v` 前缀的标签 → 推送 → 创建带自动生成说明的 Release
- [ ] 用它发出 `0.2.0`，把现状的清单版本 `0.1.0` 与远端标签 `v0.0.1` 一并拉齐
- [ ] 发完之后 `releases/latest` 返回 200，且 `tag_name` 是 `v0.2.0`
- [ ] 仓库根目录有 Windows 批处理更新脚本：切到脚本所在目录 → 检测 git 不可用时给一句人话提示 → 抓取并硬重置到远端主分支 → 暂停等待按键（不暂停则黑窗一闪而过，用户不知道成功还是失败）
- [ ] 用硬重置而非合并拉取：用户本地有改动时也必须能成功更新，不能把不懂命令行的人卡在冲突状态里
- [ ] 在一个干净目录重新 clone，不执行任何 npm 命令，扩展能加载并正常工作
- [ ] README 的快速开始与开发章节反映新的发版方式和更新脚本
