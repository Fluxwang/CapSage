# 扩展内更新检查与手动更新流程

**Status:** ready-for-agent

词汇以 `CONTEXT.md`「更新」一节为准（运行版本 / 发布版本 / 可用更新 / 更新检查 / 拉取 / 重载）。架构决定见 ADR-0011；本规格不得与 ADR-0003、0005、0010 冲突。

## Problem Statement

EchoSage 不上 Chrome 应用商店。用户是作者的几个朋友，每人手上是一份 `git clone` 出来的、以「加载已解压的扩展程序」方式常驻的工作副本。

于是出现两个谁都没法自己解决的问题：

**用户不知道有新版本。** 作者改完推上去，用户那边毫无动静，除非作者挨个去说。用了几个月的人可能一直跑在半年前的版本上，遇到早就修好的 bug。

**扩展自己更新不了。** 它跑在浏览器沙盒里，没有文件系统和 shell 访问权限，执行不了 `git pull`，也启动不了任何可执行文件。

## Solution

把「更新」这件事拆成**扩展负责发现、用户负责执行**两半，中间用一个不会说谎的提醒连起来。

扩展定时向 GitHub 问取发布版本，与运行版本做语义化比较。可用更新成立时，工具栏角标亮起、popup 顶部出现小红点。用户点进设置页的关于分区，那里有完整的两步说明：先运行仓库根目录的更新脚本完成拉取，再回到同一处点按钮完成重载。重载之后运行版本随之提高，可用更新不再成立，角标自行消失——用户不需要"知道自己更新成功了"，扩展的外观会替他确认。

关键在于提醒**没有独立的已读状态**：它纯粹是「发布版本 > 运行版本」这个不等式的投影。这让它永远不会与事实不一致，代价是把正确性押在了发版纪律上（见 Further Notes 的死锁点）。

## User Stories

### 使用者——发现更新

1. 作为使用者，我希望扩展自己定期去看有没有新版本，这样我不必记着去仓库翻提交记录
2. 作为使用者，我希望有新版本时工具栏图标上出现角标，这样我在正常用浏览器的过程中自然会注意到
3. 作为使用者，我希望这个提醒不要弹系统通知打断我，这样我在开会或看直播时不会被一个不紧急的事情打岔
4. 作为使用者，我希望提醒一直挂着直到我真的更新完，这样我不会因为随手点掉而彻底错过
5. 作为使用者，我希望点开 popup 也能看到有更新这件事，这样我不用去猜角标上那个点是什么意思
6. 作为使用者，我希望从 popup 上的提示能一键到达具体该干什么的地方，这样我不用自己在设置页里翻
7. 作为使用者，我希望在关于分区能看到我现在跑的是哪个版本、最新的是哪个版本，这样我能判断自己落后了多少
8. 作为使用者，我希望能主动点一下「检查更新」，这样我听说作者发了新版时不用干等定时检查轮到
9. 作为使用者，我希望主动检查时能看到「正在检查」和结果，这样我知道按钮确实响应了我
10. 作为使用者，我希望在已经是最新版时也能得到明确的「已是最新」答复，这样我确认自己没有落后

### 使用者——执行更新

11. 作为使用者，我希望关于分区直接告诉我该做什么，这样我不需要懂 git 也不需要来问作者
12. 作为使用者，我希望更新脚本就在仓库根目录、双击就能跑，这样我不用开命令行
13. 作为使用者，我希望脚本跑完后窗口停住显示结果，这样我能看见是成功了还是出错了
14. 作为使用者，我希望脚本在我机器上没装 git 时给一句人话提示，这样我不会只看到一行看不懂的报错
15. 作为使用者，我希望即使我之前不小心动过仓库里的文件，脚本也能成功更新，这样我不会被卡在一个我完全看不懂的冲突状态里
16. 作为使用者，我希望拉取之后能在设置页里点一个按钮就让新版本生效，这样我不用再跑一趟扩展管理页找刷新按钮
17. 作为使用者，我希望界面讲清楚"跑完脚本"和"重载扩展"是两步，这样我不会在跑完脚本发现角标还在时以为脚本失败了又跑一遍
18. 作为使用者，我希望更新之后我填的 API Key 和所有设置都还在，这样我不用每次更新都重新配置一遍
19. 作为使用者，我希望在我正捕获直播时那个重载按钮点不动并告诉我原因，这样我不会手滑弄丢正在转写的那场直播
20. 作为使用者，我希望停止捕获之后重载按钮立刻可用，这样我不必关掉设置页重开

### 使用者——异常情况

21. 作为使用者，我希望断网时扩展安静地失败，这样我的笔记本合盖一晚上不会攒出一堆我不关心的错误提示
22. 作为使用者，我希望只在我主动点检查却失败时才看到错误，这样我知道是我刚才那一下没成功，而不是系统在报警
23. 作为使用者，我希望扩展重启后不用等一整天才重新检查，这样我每天关机也不会让定时检查永远轮不到
24. 作为使用者，我希望浏览器刚启动时角标状态就是对的，这样我不会看到一个短暂的错误状态再跳变
25. 作为使用者，我希望作者回滚了某个版本时扩展不要提示我"更新"到一个更旧的版本，这样我不会被降级

### 作者——发版

26. 作为作者，我希望发一个版本只敲一条命令，这样我不会漏掉其中某一步
27. 作为作者，我希望版本号只输入一次就同时写进扩展清单和包清单，这样两处永远不会漂移
28. 作为作者，我希望发版命令自动完成构建并把产物一起提交，这样用户拉到的代码一定是能直接加载的
29. 作为作者，我希望发版命令在工作区不干净时拒绝执行，这样我不会把半成品打成一个版本
30. 作为作者，我希望发版命令自动创建带说明的 Release，这样用户看得到这个版本改了什么
31. 作为作者，我希望发版产物里不带 sourcemap，这样版本库不会因为每次全量重写的映射文件而迅速膨胀
32. 作为作者，我希望日常开发构建照旧带 sourcemap，这样我自己调试体验不受影响
33. 作为作者，我希望用户报问题时我能看懂他截图里的堆栈，这样我不必让一个不会用命令行的人去本地构建

### 维护者——代码

34. 作为维护者，我希望更新逻辑的判定部分是纯函数，这样我能用 Node 内置 test runner 直接测，不必 mock 浏览器全局对象
35. 作为维护者，我希望这个特性只引入一个测试 seam，这样它符合本仓库既有的纪律而不是另起一套
36. 作为维护者，我希望它的形状和既有的会话状态机一致，这样读过一个的人不用重新适应另一个
37. 作为维护者，我希望 service worker 和设置页里不含任何判定分支，这样测试覆盖到的就是真正会出错的地方
38. 作为维护者，我希望"为什么构建产物进了版本库"这个反常决定有据可查，这样后来的人不会把它当脏东西清理掉

## Implementation Decisions

### 单一测试 seam：更新状态机

新增一个纯逻辑模块，镜像既有会话状态机的形状——本仓库的 reducer 约定是 `(state, event) → { state, commands }`：**reducer 决定该发生什么，宿主只负责执行 I/O**。service worker 与设置页因此退化成无判定逻辑的宿主。

事件（宿主喂进来的全部输入）与指令（宿主要执行的全部副作用）：

```
events:
  { type: "host-started",        now, runningVersion, captureStatus }
  { type: "alarm-fired",         now }
  { type: "user-requested-check", now }
  { type: "check-succeeded",     now, releasedVersion, releaseUrl }
  { type: "check-failed",        now, reason }
  { type: "capture-status-changed", captureStatus }
  { type: "user-requested-reload" }

commands:
  { type: "fetch-release" }
  { type: "set-badge",   text }          // "" 表示清除
  { type: "persist",     releasedVersion, releaseUrl, lastCheckedAt }
  { type: "reload-extension" }
```

状态里同时持有一个派生视图供设置页直接渲染（按钮态、文案、是否置灰、运行版本、发布版本），设置页不做任何推导。

### 可用更新是纯投影

- 持久化的只有**发布版本**（及其 Release 链接）和上次检查时间。**不存已读状态、不存"有更新"这个布尔值。**
- 角标文本由「发布版本 vs 运行版本」当场推导。`host-started` 事件携带运行版本，reducer 据此重算角标并发出 `set-badge` 指令，**不需要发起网络请求**——这保证 service worker 每次被唤醒后角标立即正确。
- 运行版本取自扩展清单自报的版本号（设置页已有现成读取点）。

### 版本比较

- **语义化逐位比较**，只有发布版本**严格大于**运行版本才构成可用更新。
- 解析需容忍 `v` 前缀与位数不等（`1.2` 视同 `1.2.0`）；带预发布后缀的版本一律**不**构成可用更新。
- 不使用字符串不等比较：那会让作者超前的开发机误报，也会让任何一次回滚或误推的标签误报。

### 更新检查

- 端点是仓库的 GitHub **Release** 接口（`releases/latest`），**未认证**请求。仓库公开，未认证限流 60 次/小时/IP，任何合理周期都撞不到。
  - **注意**：推送一个裸标签**不会**创建 Release 对象，该端点会返回 404。因此建 Release 必须并入发版命令（见下）。
- 周期 24 小时；另外宿主启动时若距上次检查已超 24 小时，立即补一次。这条补查覆盖「用户每天关机、定时器从来轮不到」的情况。
- 扩展清单新增定时器权限。既有的全站主机权限已覆盖 GitHub API 域名。
- **失败按触发路径分流**：定时触发的检查失败后静默丢弃，不更新上次检查时间，角标沿用上次缓存的结论；只有用户主动点击触发的检查才把失败呈现到关于分区——只有那一刻用户真的在等结果。

### 提醒形态

- **只用工具栏角标**，不引入通知权限。角标常驻、不打断、不会一闪而过，匹配「不紧急但不该被错过」的语义。角标目前在本扩展中完全未被占用。
- popup 顶部的场景无关区（品牌栏）加一个小红点，点击跳转到设置页的关于分区。两个场景标签页内部都已塞满，不占用它们的竖向空间。
- 职责分离：**popup 负责告知，关于分区负责执行**。

### 关于分区

- 一个三态按钮：检查更新 / 检查中 / 发现新版本，配版本号对照与两步说明。
- **文案必须讲清拉取 ≠ 重载**：跑完脚本时磁盘已是新代码，但运行版本未变，角标仍在。不说清楚用户会以为脚本没生效而反复运行。
- 「我已拉取，重载扩展」触发扩展重载。该能力不需要任何权限，对以解压方式加载的扩展会重新从磁盘读取文件并以「更新」为由触发安装事件——等价于在扩展管理页点刷新，因此用户不必再跑那一趟。
- **捕获进行中时该按钮置灰**并说明原因。重载会连带拆掉 service worker、离屏文档与全部 content script，正在跑的捕获会被杀掉、当前字幕丢失。更新永远不紧急（角标会一直挂着），直播有时效——置灰是在保护更有价值的一边。捕获状态经既有的离屏状态查询取得，作为事件喂进 reducer。

### 更新脚本

- **只提供 Windows 批处理**一个文件。（`.sh` 在 macOS 上双击不会执行——Finder 默认关联文本编辑器，要双击得用 `.command` 后缀；目标用户都用 Windows。）
- 行为：切换到脚本所在目录 → 检测 git 是否可用，不可用则给一句人话提示 → 抓取并**硬重置到远端主分支** → 暂停等待用户按键。
- **硬重置而非合并拉取**：对纯使用者而言本地改动永远是意外，硬重置是唯一能保证「每次都能成功更新」的做法，不会把不懂命令行的人卡在冲突状态。硬重置只影响被跟踪的文件，不触碰依赖目录或任何未跟踪文件。代价：用户若真改过什么会被无声抹掉。

### 分发与发版

- **构建产物提交进版本库。** 扩展清单指向构建产物，而用户机器不装 Node——拉到的代码必须开箱即用。这是刻意违反「构建产物不进版本库」的常规，见 ADR-0011，不要"修复"它。
- **发版构建关闭 sourcemap**，日常构建与 watch 照旧带。映射文件占产物体积约三分之二且每次构建全量重写；而打包产物本来就不压缩混淆（保留文件边界注释与原始变量名），可读性不依赖它。
- **一条发版命令是唯一入口**：校验工作区干净 → 版本号同时写入扩展清单与包清单 → 关闭 sourcemap 构建 → 连产物一起提交 → 打标签 → 推送 → 创建带自动生成说明的 Release。版本号只输入一次，人不可能忘记同步。**禁止手工发版**，理由见 Further Notes。
- **首个版本号为 `0.2.0`**，把现状的清单版本 `0.1.0` 与远端标签 `v0.0.1` 一并拉齐。
- **不给扩展清单加固定公钥。** 扩展 ID 继续由加载目录的绝对路径推导；原地拉取保证路径恒定，本地存储（本扩展全部设置与 API Key 的唯一落点）因此在更新前后是同一份。代价：用户挪动文件夹、换盘或重装系统后克隆到别的路径会丢配置——这正是不采用「下载压缩包解压」方案的原因。

## Testing Decisions

**好测试的标准**：只测外部行为。对 reducer 而言，外部行为就是「喂进一个事件序列，得到什么状态和什么指令」——不断言内部字段怎么组织，不为了可测性而导出中间函数。

**prior art**：既有的会话状态机测试就是范本（六十余个用例，全部形如"构造状态 → 派发事件 → 断言状态与指令"，不 mock 任何浏览器全局对象）。新测试沿用同样的导入方式、同样的断言风格、同样的中文用例命名。

**被测模块**：只有更新状态机。它是本特性唯一的 seam，符合"纯逻辑模块不经 bundler、由 Node 内置 test runner 直接导入"的既有纪律（ADR-0010）。

**必须覆盖的行为**：

- 版本解析：`v` 前缀、位数不等、预发布后缀、非法或缺失输入
- 严格大于才构成可用更新；相等不提醒；发布版本更旧不提醒（回滚场景）
- 宿主启动时用缓存的发布版本重算角标，**不发出** `fetch-release` 指令
- 宿主启动时距上次检查超期，**发出** `fetch-release`；未超期则不发
- 定时事件触发检查；检查成功写入新的发布版本与检查时间并重算角标
- 定时触发的失败被静默吞掉：不更新上次检查时间、不改角标、不产生面向用户的错误
- 用户主动触发的失败产生面向用户的错误态
- 检查进行中重复触发不会发出第二条 `fetch-release`
- 捕获状态为捕获中或重连中时，重载按钮态为禁用；转为空闲后恢复可用
- 捕获进行中收到重载请求不产生 `reload-extension` 指令
- 可用更新成立时重载请求产生 `reload-extension` 指令
- 运行版本提高到与发布版本相等后，重算得到的角标为清除

**不写的测试**：service worker 的定时器注册、GitHub 响应的网络往返、设置页 DOM 绑定、批处理脚本。它们要么是宿主的薄 I/O，要么不在任何可自动化的 seam 上。

## Out of Scope

- **Native Messaging**——唯一能让扩展自己执行拉取的路径，但要求每个用户额外安装并注册一个本地宿主程序，对这个规模成本过高。见 ADR-0011。
- **上架 Chrome 应用商店**——审核成本与隐私政策负担不划算，且上架后更新机制完全不同，本规格将失去意义。
- **在 Release 里附带打包好的扩展压缩包**——解压通常落在带版本号的新目录，换路径即换扩展 ID，本地存储随之清空，用户每次更新都要重填 API Key 和全部设置。
- **「忽略此版本」或稍后提醒**——需要引入第二份状态，与「可用更新是纯投影」的核心设计冲突。
- **失败后指数退避重试**——24 小时周期加启动补查已是极宽松的时限，重试只会平添状态机分支。
- **macOS / Linux 的更新脚本**——目标用户都用 Windows；README 里给一行命令即可。
- **自动更新**（扩展自己拉代码并重载）——浏览器沙盒里做不到。
- **关于分区「更新日志」链接的改造**——该链接目前指向一份 ADR，属占位。开始创建 Release 后它应指向最近一次 Release 页面（检查时顺手缓存链接，reducer 的 `persist` 指令已为此预留字段）。是否并入本次实现由作者决定。

## Further Notes

### 死锁点：本设计唯一的失败模式

角标是「发布版本 > 运行版本」的纯投影，不存已读状态。若打了新标签却忘了同步提高扩展清单里的版本号，用户拉取并重载之后运行版本仍是旧值，**不等式依然成立，角标永远消不掉**。用户会反复运行脚本、怀疑更新没生效，而且**完全无法自救**——他既看不出问题在哪，也没有任何界面能清除这个提醒，只能来找作者。

派生状态的收益是永不与事实不一致，代价就是把正确性全部押在「标签与清单版本永远同步」上。这是发版命令必须是唯一入口的唯一理由，也是它必须校验工作区干净的原因。任何"就这一次手动打个标签"都会引爆它。

### 拉取与重载必须在界面上被讲成两件事

这是最可能产生用户困惑的地方，且困惑的方向恰好是"以为失败了"。用户跑完脚本时磁盘上已是新代码，但已加载的那份没变，角标还在。界面若只说"运行 update.bat 即可更新"，用户会重复运行脚本直到放弃。

### 当前仓库状态
