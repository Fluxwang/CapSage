# 视频字幕场景的兜底转写改用 AssemblyAI 实时流，播完一轮自动停止

视频字幕场景（原 TikTok Caption Studio）里，没有原生字幕的视频过去是固定录 30 秒标签页音频、一次性发给 Whisper 拿 `verbose_json` 分段结果——一种有界的批量模式。合并后改成复用直播实时场景（原 EchoCap）那套 AssemblyAI 实时流式转写：开始播放就建 WebSocket 连接，边放边转写，产出结构和直播场景相同的"话轮"。

这带来一个直播场景不存在的新问题：TikTok 视频（无论是信息流还是详情页）默认循环播放，`<video>` 不会触发真正的 `ended`，播完就跳回开头继续放。如果转写会话跟着播放状态无限跑下去，一条用户长时间停留的循环短视频会被反复转写同样的音频，产生持续的 AssemblyAI 费用（按 WebSocket 连接时长计费，不按内容去重）,不像旧的 30 秒批量模式天然有一个固定成本上限。

## 决定

转写会话在这段视频**播完一轮**后自动停止定稿，不管视频是否继续循环播放。判定方式：监听 `timeupdate`，当 `currentTime` 从接近 `duration` 跳回接近 0 时，视为完成一轮。

## 考虑过的替代方案

- **不做循环检测，只复用直播场景现成的会话硬上限/长静音断连**（ADR-0005）：实现最简单，但如果视频比硬上限短很多，还是会被重复转写好几遍才触发上限，达不到"成本可预期"的目的。
- **只跟着"当前活跃视频"这个已有信号走**（用户划走才停）：完全复用现成基础设施，但同样不处理循环重复转写的问题，而且"这条视频的字幕"这个概念会变成"用户停留在这条视频期间产生的字幕"，两者在循环播放下不是一回事。

"播完一轮"胜出的原因是它利用了视频字幕场景相对直播场景的一个本质差异——**视频有已知的、有限的时长**（`video.duration` 随时可读，不受 `loop` 影响），直播没有。这个差异值得在转写停止逻辑里体现出来，而不是用一套对两个场景都通用但对视频场景次优的策略。

## 后果

- 视频字幕场景的转写停止逻辑不能直接照搬直播场景的会话状态机，需要一个新的、基于播放进度的停止信号,与长静音断连/硬上限并存（三者任何一个先触发都停）。
- 这个"播完一轮"判定应该写成一个不碰浏览器 API 的纯函数（输入是一串 `currentTime` 采样和 `duration`，输出是否已完成一轮），复用 `CONTEXT.md` 里"单轮转写"这个术语，并落在 `core/` 这个既有的纯逻辑测试 seam 里。
