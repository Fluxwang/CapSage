# 只用浏览器内置 Translator API，不做云端翻译兜底

受众是作者本人和少数几个朋友，都用 Chrome 或 Edge。翻译**只**走浏览器内置的 `Translator` API，明确不实现 Azure AI Translator 之类的云端兜底。

## 为什么这不是「只支持 Chrome」

内置 `Translator` 是同一套 Web API，Chrome 138+ 和 Edge 148+ 都实现了（微软的实现同样是本地模型、同样免费、同样对扩展开放）。所以「用 Edge 的人」零成本覆盖，不需要为此引入第二个翻译方案。

而 Firefox 和 Safari 从来就不在讨论范围内——这个扩展依赖 `chrome.tabCapture` 和 `chrome.offscreen`，两者都不支持，换什么翻译方案都救不了。

真正覆盖不到的只有：Brave / Vivaldi / Opera 这类不带 Google AI 模型组件的 Chromium 分支，以及低于版本线的老浏览器。这些情况**明确不支持**，靠启动时的能力检测给出清晰提示，而不是靠兜底路径。

## 为什么不做云端兜底

按 1–2 小时/天的使用量估算，西语语速约 180 词/分（含空格约 1080 字符/分钟），按 65% 语音密度算约 **250 万字符/月**——已经超出 Azure Translator 免费档 F0 的 200 万字符/月，落到付费档意味着每月成本比 AssemblyAI 那部分还高。

但成本不是主要理由。主要理由是云端兜底会连带拖出一整套东西：第二份 Key 的存放与填写界面、`host_permissions`、配额监控、云端失败时的降级路径、两条链路的延迟差异。而它服务的受众是「用 Brave 且愿意自己去 Azure 申请 Key 的人」——这个交集基本是空的。

## 后果

- 翻译调用仍然收拢在**单一模块**后面。这不是为了将来换供应商而做的抽象，只是不让 `Translator.create()` 散落在各处；成本接近零。
- 启动时必须检测 `Translator` 是否存在、`availability()` 是否可用，并对不支持的浏览器给出明确文案，而不是静默失败。
- 每个使用者填自己的 AssemblyAI Key，所以 `manifest.json` 需要 `storage` 权限（目前**没有**）并配一个填 Key 的界面。
- 如果哪天受众扩大到「任意 Chromium 用户」，这个决定要重新评估——届时代价是上面那一整套，不是加一个 if 分支。

## 合并进 EchoSage 后的唯一例外（2026-09）

**视频字幕场景**可以选择「AI 模型」作为翻译引擎，走云端 chat completions 接口（见 ADR-0008）。这不推翻本决定，因为上面那套成本论证的前提是「直播连续翻译 1–2 小时/天」——视频字幕是有限时长、按需触发、且只在用户主动选择时才走云端，量级完全不同。

**直播实时场景仍然严格适用本决定**：翻译只走浏览器内置 `Translator`，不提供任何云端选项。上面关于能力检测、不支持的浏览器给明确提示、翻译调用收拢在单一模块后面的几条后果，对两个场景都继续有效。
